# Admin modules and operator onboarding

Implementation review: 1 November 2026. Scope: the 50 resources and 10 pages registered in the admin panel, including the new Invitations resource and Onboard operator page. Shared operational resources also appear in the operator portal when the user's permissions allow them.

This is a code and automated workflow audit, not an assertion that live staging or production has been updated. No live records were changed by this work.

## Onboard a client/operator

1. Sign in to **Administration** with organization management, invitation management and role delegation permissions. Select **Onboard operator** in the sidebar, directly below **Dashboard** in the default order, or open **Organizations → Onboard operator**.
2. **Organization:** create the operating company with a unique code, or select an existing active operator. Codes are saved in uppercase. This wizard creates charge-point operators; customer Business/Fleet charging accounts remain a separate workflow.
3. **Administrator:** enter the recipient's work email and choose an eligible operator role. Roles must include Operator panel access, must exclude Administration panel access, and cannot grant permissions the inviting admin does not hold.
4. **Access:** choose all sites belonging to this operator, or one existing site for an existing operator. Organization access also covers sites assigned to that operator later. It does not grant tenant-wide finance, inventory or platform settings access.
5. **Review:** check the organization, email, role and scope, then select **Create and invite** once. The organization, invitation, request identifier and audit entries are saved together. Repeated submission of the same request does not create a second organization or invitation.
6. The recipient opens the invitation email. New users enter their name, password and password confirmation. Existing users retain their password. Acceptance does not sign anyone in automatically; the recipient signs in at `/operator/login` afterward.
7. Open **Identity and audit → Invitations** to check pending, expired, accepted or revoked status. **Send new link** invalidates the old link and queues a fresh seven-day invitation. **Revoke** cancels an unused link. After acceptance, suspend membership or remove role access in **Operator users** instead.
8. Create or update the operator's **Site**, then use **Charging stations → Setup guide** for stations, EVSEs, connectors, operating hours and pricing. Verify the assigned operator and site access before publishing a location.

An invitation is **queued**, not proof of delivery. SMTP and a working notification queue are required. Disabled accounts, suspended memberships and conflicting existing organization memberships need admin review; an invitation cannot silently restore or move them.

## Module audit and available actions

“Protected” means the records are generated by their owning workflow and must not have arbitrary create/edit/delete buttons. Corrections must preserve financial or operational evidence. All actions remain permission- and tenant-scoped; menu visibility alone is not authorization.

### Maintenance

| Resource | Available administration |
|---|---|
| Work orders | **Added:** create a corrective, inspection or vendor-repair work order; existing guarded Change state action remains. Assignment, detailed planning, checklists and resolution evidence still use their existing maintenance API workflows. |

Date and runtime intervals are seconds (daily: 86,400; weekly: 604,800), energy is Wh, and session count is a whole number. Date schedules also require the next due instant, shown in UTC. Pausing a plan retains historical work orders.

## Access and implementation changes

- Active charge-point-operator organization grants now authorize the organization's owned sites consistently in list queries and detail policies. Other operators' sites remain excluded.
- Operator-panel entry accepts eligible organization/site-scoped roles. Admin-panel access still requires its tenant-wide grant.
- Operator-user lists are scoped to permitted memberships, rather than exposing every membership in the tenant.
- Invitation acceptance rechecks expiry, revocation, inviter authority and organization activity under a lock. It cannot raise the recipient above the inviter's authority.
- Notifications use the dedicated `invitations` queue after commit and are encrypted in the queue. Invitation tokens are stored hashed; tokens and passwords are excluded from audit entries.
- New maintenance and purchasing mutations write audit entries; inventory actions preserve existing ledger and approval controls.

## Deployment and verification

Apply `2026_11_01_000003_create_operator_onboardings.php` with the normal reviewed release migration step before using the wizard. It is additive and does not alter existing business records. It stores tenant, organization, invitation and actor references plus a request digest for retry protection. Retain these references with the existing access/audit retention policy; do not drop them as an application rollback. Roll back application code or use a reviewed forward migration if needed.

Rebuild Vite assets and clear/rebuild application views through the normal deployment process. Ensure the queue worker runs with the new notification code and existing SMTP configuration. Keep the production worker on App01 under the current deployment design; this change does not add a worker to App02.

Automated coverage includes all registered admin resource/page routes, valid and invalid onboarding, duplicate submission, cross-tenant role rejection, organization/site isolation, invitation replay/resend/revoke, disabled-account rejection, maintenance creation/plan controls, draft preservation, independent adjustment approval, stock transfers/counts, goods inspection/posting, invoice matching and session review validation. Tests use isolated data and fake notifications; they do not send invitations to clients.

Before release acceptance, perform a staging browser pass with one admin and one invited operator: desktop/mobile layout, dark/light mode, email delivery, invite acceptance, assigned-site access and the actions relevant to that operator. Passing server-render tests does not replace that visual and delivery check.

Local verification: **372 PHP tests / 3,334 assertions**, PHPStan (zero errors), full Pint check, Vite production build and **11 JavaScript map tests** passed. Composer validation/audit and npm audit passed with zero reported vulnerabilities. The npm scan initially identified existing advisories; eight compatible dependency updates in `package-lock.json` were reviewed, rebuilt and rescanned. No dependency major-version requirement changed. Browser visual verification was unavailable because the local browser automation runtime failed to initialize (`failed to write kernel assets`).

## Other wizards recommended for a later decision

1. **Station commissioning:** extend the existing setup guide into a validated sequence for site → station/OCPP identity → EVSE/connectors → hours → tariff → connection test → publish. Highest priority after operator onboarding.
2. **Procurement sourcing:** request → RFQ/suppliers → quotations → comparison → approval → order. This would remove the current dependency on API/setup tooling for approved comparisons.
3. **Stock receiving/counting:** barcode/item selection → quantities → discrepancies → independent approval → posting. Useful when warehouse staff handle many items.
4. **Tariff scheduling:** rates → applicable locations/connectors → effective dates → sample cost preview → publish. Keep existing-session prices unchanged.

Only operator onboarding was implemented as a new wizard. These four are recommendations, not enabled flows.
